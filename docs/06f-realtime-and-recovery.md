# 여섯 번째 구현 — 실시간 화면 반영과 누락 복구 처리

현재 **6.1 MVP 구축 중**. 외부 계정 없이 검수한 내부 구현이며 Emergent 실연결·5초 p95 목표·전체 운영 검수의 완료와 구분한다.

## 실시간 화면 반영

접수와 업무 변경을 DB에 저장할 때 같은 트랜잭션에 변경 기록을 남긴다. 회사별 커서를 트랜잭션 안에서 증가시켜 뒤늦게 커밋된 기록을 건너뛰지 않도록 했다. 새 문의 중복 요청과 롤백은 불필요한 변경 기록을 만들지 않는다.

`GET /api/v1/events`는 로그인된 브라우저에 SSE를 제공한다. 기본 1초 간격으로 영속 변경 기록을 확인하고, 필요한 목록을 다시 조회할 수 있도록 상담 ID만 전달한다. 상담 내용·전화번호·이메일은 이벤트로 보내지 않는다.

- `ready` / `reset`: 최신 목록 재조회. 보관 범위 밖이거나 잘못된 미래 커서이면 안전하게 전체 재조회한다.
- `change`: 접근 가능한 상담 변경. 재배정으로 권한을 잃은 전 담당자에게는 상담 ID 없이 새로 조회하라는 신호만 보낸다.
- `checkpoint`: 읽은 위치 갱신. `Last-Event-ID`로 다른 API 인스턴스에서도 재생할 수 있다.
- `heartbeat`: 연결 유지 확인.
- `session-expired`: 세션 만료·로그아웃·역할 변경 시 연결 종료 및 재로그인 안내.
- `unavailable`: 일시 조회 실패, 브라우저 자동 재연결.

매 확인마다 세션과 최신 담당자를 검증한다. 사용자당 API 프로세스별 연결은 최대 5개이며 느린 수신자와 종료된 연결의 타이머를 정리한다. 서버 종료 시 활성 SSE도 닫는다. 프로덕션의 전체 연결 수 제한·로그 보존/정리 정책·부하 검증은 후속이다.

업무 화면은 변경 신호를 모아 재조회하며 모달 입력은 유지한다. 연결 장애 시 15초 조회로 전환하고 안내한다. 포커스 복귀 시에도 조회한다. 연결 중에는 시간에 따라 바뀌는 기한 상태를 위해 1분마다 조회한다. 운영 설정·성과·알림·연동 상태 화면은 각 화면의 조회 방식을 유지한다.

## 누락 복구 처리 엔진

`recoveryService`는 서버 내부의 신뢰된 `fetchPage({tenantId,cursor,limit,signal})` 어댑터를 받는다. 현재 실제 외부 어댑터는 주입하지 않았다. 응답 계약은 `{items: 문의 이벤트 배열, nextCursor: 문자열, hasMore: boolean}`이며 최대 100건이다. 문의 이벤트는 서명 수신과 같은 스키마·동일 저장 함수를 사용한다. 내부 가져오기 함수는 서명 없는 HTTP 경로로 노출하지 않는다.

1. 회사별 실행 임대를 확보한다. 다른 실행이 진행 중이면 중복 실행하지 않는다.
2. 마지막 성공 위치로 조회한다. 10초 응답 제한과 중단 신호를 적용한다.
3. 각 문의를 저장한다. 일부 오류가 있어도 페이지의 다른 문의는 검사하되, 오류를 영속 목록에 남긴다.
4. **페이지의 모든 문의가 성공한 뒤에만 커서를 전진시킨다.** 중간 실패나 응답 유실 후 같은 페이지를 다시 읽어도 상담·업무·알림은 중복 생성되지 않는다.
5. 처리 중에는 60초 실행 임대를 갱신한다. 종료된 실행의 임대가 만료되면 다음 실행이 이어받는다.
6. 성공·일시 실패는 다음 실행 가능 시각을 기본 60초 후로 기록한다. 요청 제한은 제공된 대기 시간을 적용하고 인증 오류는 관리자 확인 전 중단한다.

실제 60초 예약 실행·Emergent HTTP 조회 어댑터는 아직 연결 전이다. 임대와 `next_run`은 이를 연결할 때 사용할 실행 제어이며, 그 자체가 외부 자동 조회를 실행하는 것은 아니다. 원문 오류는 ID·상태·안내·발생 시각만 오류 목록에 남기고 원본 조회 위치를 유지한다. 잘못된 원본을 수정하여 다시 수신하면 같은 오류를 해결 표시한다.

## 관리자 화면·API

`/live/integrations`의 ‘외부 문의 연결’에서 연결 준비 여부, 마지막 수신, 보충 상태, 미해결 오류 최근 100개를 확인한다. 미연결 상태에는 실행 버튼을 비활성화하고 ‘오류 없음’을 ‘연결 검증 성공’으로 표시하지 않는다.

| API (`/api/v1` 기준) | 기능 |
|---|---|
| `GET /admin/integrations/emergent` | 관리자 회사의 연결·수신·복구 상태 |
| `POST /admin/integrations/emergent/recover` | 설정된 어댑터로 현재 페이지 한 번 확인. 미설정이면 503 |
| `POST /admin/integrations/emergent/resume` | `confirmed:true`로 인증 설정 확인 후 중단 해제. 미설정이면 503 |

## 검수 결과

- 기존 검사와 신규 SSE·복구 검사를 포함한 자동 검사 38개 통과. 타입 검사와 웹 빌드 통과.
- 실제 HTTP SSE 연결에서 신규 문의 전달, 다른 서버 객체로 재연결 후 누락 변경 재생, 로그아웃 종료, 최대 연결 수 제한을 확인했다. 공유 PGlite로 확인했으며 실제 PostgreSQL 복제 배포 검증은 아니다.
- 담당자·회사별 정보 범위, 재배정 후 ID 없는 갱신, 커서 초기화, 트랜잭션 롤백을 확인했다.
- 복구의 일부 오류·커서 유지·수신 중복·인증 중단·관리자 재개·요청 제한·만료 임대 회수를 격리 DB에서 확인했다.
- 임시 메모리 DB의 브라우저 두 탭에서 문의 접수 후 열린 업무 화면의 건수가 0→1→2로 자동 반영됨을 확인했다. 두 번째 접수 때 작성 중인 미저장 메모가 유지됐다.
- 임시 서버를 중단하여 실시간 연결 복구 및 15초 조회 안내를 확인했다. 관리자 연결 화면도 확인했다.
- 브라우저 검수는 `scripts/live-realtime-review.mjs`의 별도 메모리 DB에서 수행했다. 사용자가 입력한 실제 로컬 상담을 수정하거나 검수 예시를 추가하지 않았다. 종료 후 예시 DB는 남지 않는다.

전체 모바일 회귀 검수·실제 네트워크 지연·로그 보존 정책·운영 DB/서비스 구성·외부 어댑터와 예약 연결·메일·AI·승인 배포는 [첫 배포 작업 목록](06-first-release-checklist.md)에 남아 있다.

### 검수 중 서버 중단 복구

사용자가 화면 중단을 알린 뒤 로컬 4180 서버 응답이 없음을 확인했다. 저장 파일은 유지됐으며 숨김 백그라운드 프로세스로 다시 시작하여 health 응답, 기존 직원 로그인·상담 기록, SSE 정상 연결을 확인했다. PowerShell 재실행 도구는 `scripts/start-live.ps1`이며 컴퓨터 재부팅 후 자동 실행을 설정한 것은 아니다.
