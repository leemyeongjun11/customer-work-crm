# 프레임 02 — 전체 화면 검수와 모바일 접속

상태: **5.1 프레임 목업 / 사용자 검수 대기**. 2026-09-12.

## 변경 요청과 적용

- 휴대폰에서도 목업을 확인한다.
- UI 의사결정 전에 목업 범위를 전체 화면으로 넓힌다.
- 모든 화면을 열고 정상·빈 상태·실패·권한·확인창을 검수한 뒤 다음 단계로 넘어간다.
- Tailwind CSS와 shadcn 기본 Neutral 테마를 유지한다. 최종 테마는 아직 선택하지 않는다.

‘전체 화면’은 브라우저 전체 화면 모드가 아니라 **현재 정의된 업무의 전체 화면 범위**를 의미한다. 상세 탭과 확인창도 독립 검수 항목이다. 52개 항목은 [화면 목록](05c-screen-inventory.md)과 웹 `/review`에 동일하게 정리했다. 새로운 기능이 생기면 이 목록에 검수 항목부터 추가한다.

## 검수 방법과 단계 완료 조건

상단 진행 현황은 **PC 완료 / 모바일 완료 / 모두 완료**로 나누어 표시한다. PC만 확인하면 PC 완료 수가 즉시 증가한다. ‘모두 완료’는 같은 화면의 PC와 모바일이 모두 확인 완료인 항목 수이며, 최종 단계 완료 조건에는 이 수를 사용한다. 기존 검수 선택과 의견은 유지한다.

1. PC에서 `/review`를 연다. 구역을 선택하고 `화면 열기`로 해당 화면을 확인한다.
2. 모바일에서도 같은 화면의 읽기·입력·버튼·스크롤을 확인한다. 길이가 긴 고객명/초기 요청은 카드 밖으로 넘치지 않는지 확인한다.
3. PC/모바일 각각 `미확인`, `수정 필요`, `확인 완료`로 표시하고 수정 의견을 남긴다.
4. 피드백을 전달한다. 제작자가 수정하면 해당 항목을 다시 검수한다. 한쪽이 수정 필요이면 전체 완료로 집계하지 않는다.
5. 모든 항목의 PC와 모바일이 확인 완료여야 `전체 검수 완료 확인`이 활성화된다. 사용자가 직접 완료로 확인한 이후 다음 대화에서 **5.2 UI 의사결정**을 시작한다.

작성 예: `상세·자료 / 모바일에서 파일명이 길어 버튼 위치가 불편함 / 파일명을 별도 줄로 배치`.

사용자 검수 기록은 브라우저의 localStorage에 저장한다. 주소(호스트·포트)와 기기가 달라지면 별도 기록이다. 휴대폰 의견을 PC에 합쳐 입력하거나 JSON 내보내기로 전달한다. 자동 병합·클라우드 동기화는 없다. 파일 내보내기 버튼으로 다운로드 링크를 만든 뒤 링크를 누른다. 민감한 정보 없이 화면에 관한 피드백만 입력한다.

## 모바일에서 열기

현재 실행 중인 휴대폰용 주소: **http://172.30.1.69:4174/review**.

1. 휴대폰을 이 PC와 같은 Wi-Fi에 연결한다.
2. 휴대폰 브라우저 주소창에 위 주소를 입력한다.
3. 오른쪽 위 `전체 메뉴`에서 오늘 할 일·영업건·관리 화면·검수 도구에 접근할 수 있다.

이 PC와 미리보기 서버가 실행 중이어야 한다. Wi-Fi 주소는 네트워크 변경 시 달라질 수 있다. 모바일 데이터(4G/5G)만 사용하는 외부 접속 주소가 아니다.

다시 실행할 때 프로젝트 폴더 터미널에서:

```powershell
pnpm build
pnpm --filter @crm/web preview:mobile
```

실행 결과의 `Network` 중 Wi-Fi 주소를 사용한다. 휴대폰에서 localhost 또는 127.0.0.1을 입력하면 휴대폰 자체를 가리킨다. 접속이 안 되면 같은 Wi-Fi인지 확인하고 Windows의 해당 Node 미리보기 허용 여부나 공유기의 기기 간 접속 제한을 확인한다. 방화벽 전체를 끄지 않는다.

서버는 4174 포트로 네트워크에 바인딩한다. 종료하려면 실행 터미널에서 Ctrl+C. PC 전용 기존 4173 미리보기와 별도 프로세스다. 공유기 포트 개방이나 인터넷 공개 배포는 하지 않았다.

## 기능별 시연과 실제 연결의 경계

| 구역 | 목업에서 수행하는 것 | 실제 연결 전인 것 |
|---|---|---|
| 접수 | 개인/기업 입력, 필수값 검사, 실패/성공, 현재 탭 CRM에 담당자·기한 연결 | Emergent 수신, 실시간 기기 간 공유, 중복 접수 트랜잭션 |
| 로그인·초대·재설정 | 폼, 실패·만료·접수 안내, 검수 역할 변경 | 실제 인증·계정·이메일·보안 격리 |
| 업무·영업건 | 기존 완료·기한·다음 행동·메모·단계·제안·원문 조회, 메모/업무 제목 수정과 이력 | 서버 버전·트랜잭션·실시간 동시 편집 |
| 자료 | 선택 파일의 이름/크기 검사, 목록, 미리보기 영역 | 내용 읽기, 업로드, 실파일 다운로드, 발송 첨부 |
| AI 변경 | 가상 근거와 전후 비교, 지정 예시 업무 되돌리기, 후속 변경 차단 | 실제 AI 근거 생성·버전 검사·일반화된 되돌리기 |
| 알림 | 15:00·16:30 대상 미리보기, 영업건 이동 | 실제 예약·메일 발송·도달 결과 |
| 성과 | 가상 첫 연락 업무의 원래 기한 기준 완료율, 100% 목표 구분 | 전체 이력 기반 KPI·운영 집계·제외 정책 검증 |
| 실행 상세 | 대기/실행/성공/실패/인증/제한/결과 불명, 조회 전 재실행 차단 | 실제 대기열·제공자 결과 조회·재실행 |
| 사용자 | 초대 목록, 중복 이메일 안내, 역할 변경, 진행 건이 있으면 비활성 차단 | 실제 접근 토큰 회수·계정 생성·권한 적용 |
| 운영 기준 | 새 가상 접수 기본 담당자 반영, 휴일 값과 변경 확인 화면 | 휴일 계산·정책 버전·예약 시간 변경 |
| 외부 연동 | 정상/인증 만료/API 변경/데이터 오류/요청 제한/비용 한도 안내 | 실제 자격 증명 갱신·API 호출·예산 차단 |
| 공통 상태 | 로딩·권한·404·충돌·잘못된 값·저장 실패·연결 지연과 복구 동선 | 실제 API 응답 기반 예외 처리 |

업무·설정·초대·자료의 시연 변경은 현재 탭 메모리에만 남는다. 새로고침하면 초기화되며 PC와 휴대폰이 공유하지 않는다. 검수 의견만 브라우저에 저장된다. 실제 고객 정보나 인증 비밀값을 받는 운영 서비스가 아니다.

기존 이메일 승인 흐름은 즉시 성공을 보여주는 가상 동작이다. 새 실행 상세는 대기→성공/실패의 화면 검수 예시이며 서로 실제 큐로 연결되어 있지 않다. 운영 시에는 반드시 202 queued와 실제 성공을 분리해 완료 처리한다. 초대/재설정/자료 용량 등 이번에 추가한 세부 화면은 검수 제안이며 아직 최종 UI 결정이 아니다.

## 제작자 검증 — 사용자 검수와 별도

- `pnpm check`: 타입 검사, 테스트 19개, 프로덕션 빌드 통과.
- 휴대폰 일반 HTTP 환경에서 `crypto.randomUUID`가 없더라도 접수·기록이 가능하도록 `getRandomValues` 기반 ID 대체 경로 추가 및 테스트.
- 브라우저 390×844와 1440×1000 뷰포트 설정으로 각각 52개 화면 URL 진입, 본문 표시, 확인창 열림과 문서 가로 넘침 검사. 실패 0건. 브라우저 패널 확대율로 CSS 실제 측정 폭은 설정값과 다를 수 있음.
- 모바일 크기에서 기업 접수 실패→입력 보존→재시도→담당자와 첫 연락 기한 연결 확인.
- PC 브라우저에서 휴대폰용 LAN 주소로 개인 문의 접수 성공 확인. **실제 휴대폰 하드웨어에서의 터치·키보드·브라우저 호환 검수는 사용자 확인 대기**.
- 결과 불명 작업은 결과 조회 전 재실행 버튼 비활성, 미접수 확인→사용자 확인→대기 상태 복구 검증.
- 모바일 전체 메뉴에서 AI 역할 전환→사용자 관리 접근 차단→관리자 복귀 확인.
- 검수 집계 0/52, 단계 완료 버튼 비활성 확인. 제작자 검증으로 사용자 항목을 완료 처리하지 않음.

화면에 존재하는 모든 업무 조합·운영 보안·성능의 검증을 뜻하지 않는다. UI 의사결정은 전체 사용자 검수와 수정 반영 후 진행한다. Railway 운영 환경·GitHub 승인 배포는 이번 로컬 목업 변경으로 활성화하지 않는다.
