## 시작 시점의 실제 상태

- React·Tailwind CSS·shadcn 기반 전체 프레임과 가상 데이터 업무 처리 구현.
- 화면의 시연 상태와 실제 저장·발송·인증을 구분해야 함. 현재 업무 변경은 새로고침하면 초기화되고 기기 간 공유되지 않음.
- `apps/api`, `apps/worker`, `apps/scheduler`는 안내 문서만 존재. PostgreSQL, 실제 인증, Emergent, 메일, AI 연결은 미구현.
- GitHub Actions·Railway 설정과 배포 검증 스크립트 존재. 로컬 Git 원격 저장소 미등록. 실제 CI/CD 성공 이력과 클라우드 연결은 확인되지 않음.
- 기존 테스트 21개 통과 기록은 가상 업무 규칙·배포 검사 등의 검증이며, 실제 서비스 전체 검수 완료를 뜻하지 않음.

사용자는 프레임 검수 완료를 알리고 6차 진행에 동의했다. 현재 수정된 화면과 shadcn 기본 테마를 초기 구축 기준으로 사용한다. 브라우저의 개별 검수 결과를 자동 변경하지 않으며 미해결 UI 피드백은 6차 안정화 목록에 연결한다.

위 ‘시작 시점’ 이후 실제 로그인·회사/담당자 권한·상담 접수·담당자/기한 배정·연락 결과·업무·메모·이력을 API와 로컬 파일 DB에 연결했다. 중복 처리·버전 충돌·재시작 유지 검사를 추가했다. 로컬 Worker/Scheduler와 운영 기준·성과 집계까지 구현했으며 외부 서비스·독립 운영 서비스·실제 배포는 아직 구현·검증 전이다.

## 6.1 MVP 범위 구축

### 공통 핵심 범위 — 작은 단위로 구축·검수

| 기능 묶음 | 실제로 구현할 동작 | 사용자 검수 기준 |
|---|---|---|
| 로그인·회사·권한 | 회사별 데이터 분리, 관리자/직원 접근, 세션 만료 처리 | 직원이 권한 밖 영업건과 관리 설정에 접근할 수 없음 |
| 신규 상담 접수 | 입력 검사, DB 저장, 기본 담당자와 첫 연락 기한 연결, 원문 보존 | 새로고침·재로그인 후에도 문의 유지, PC와 모바일에서 같은 건 조회 |
| Emergent 수신 | 웹훅/API 어댑터, 중복 방지, 누락 보정 | 같은 문의를 재수신해도 중복 생성·CRM 수정본 덮어쓰기 없음 |
| 업무·영업건 | 단계 관리, 유형별 다음 행동, 기한 미정, 상담 메모·고객 수정 | 입력한 실제 데이터로 오늘/예정/확인 필요와 상세가 일치 |
| 첫 연락 수행 | 통화 연결 또는 부재 후 문자 발송 기록, 실제 수행 시각 | 전화 시도만으로 완료되지 않음. 실제 연락은 직원이 수행 |
| 변경 확인·이력 | 기한 변경 이유, 완료 취소, 종료·담당자 변경 확인, 전후 이력 | 중요한 변경은 권한과 확인 절차를 거치며 과거 기록 보존 |
| 이메일 알림 | 접수 확인 및 영업일 15:00/16:30 알림, 결과 저장, 재시도 | 검수 수신함에서 수신 확인. 실패를 성공으로 표시하지 않음 |
| 안정적인 저장 | 서버 검증, 버전 충돌, 영속 작업 큐 | 중복 클릭·재시작으로 업무나 이메일이 중복 실행되지 않음 |

우선 사용자가 시작을 요청한 공통 핵심 업무부터 구현한다. 첫 전달은 저장·권한 흐름이며, AI를 전체 요구사항에서 제외하는 결정은 하지 않았다. 외부 제공자 연결 단계에서 실제 AI 범위와 배포 시점을 확인한다.

AI를 포함할 경우 기존 권한 계약을 유지한다. 영업 기록·근거 있는 다음 행동은 허용 범위에서 직접 반영하고, 기한 근거가 없으면 미정으로 둔다. 종료·담당자 변경·고객 후속 발송은 사람 확인이 필요하다. AI에 사용자·권한·시스템 설정 변경을 허용하지 않는다.

MVP 여부와 별개로 전체 제품의 기존 요구사항은 삭제하지 않는다. 파일 저장·첨부, 상세 KPI, 사용자 초대/재설정의 공급자 연동, AI 확장, 고객 후속 메일은 핵심 흐름과 함께 우선순위를 확정해 첫 배포 또는 추가 구축으로 배정한다.

### 구축 순서

1. 데이터 모델·DB 마이그레이션·API 기반·인증/권한을 마련한다.
2. 첫 실제 연결 단위로 **상담 접수 → DB 저장 → 담당자·기한 → 오늘 할 일 → 결과 기록**을 완성해 검수를 요청한다.
3. 다음 행동·메모·단계·변경 확인과 이력을 연결한다.
4. Worker/Scheduler와 검수용 메일 수신함을 연결해 알림을 검수한다.
5. 사용자 선택에 따라 AI 분석과 제안 흐름을 추가하고 실제 근거·실패·승인 경계를 검수한다.

외부 서비스 연결 전에도 로컬 서버·테스트 DB·제공자 대체 어댑터로 독립 구현을 진행할 수 있다. 대체 어댑터의 성공을 실제 외부 연동 성공으로 보고하지 않는다. Emergent 접근이 준비되지 않으면 자체 접수 API로 핵심 흐름을 검수하되, 원래 연동 요구는 미완료로 추적한다.

## 6.2 검수 및 안정화

화면 확인과 실제 업무 검수를 구분한다. 각 묶음마다 ‘검수 위치 / 준비 데이터 / 수행할 행동 / 예상 결과 / 확인 결과 / 수정 내역’을 기록한다. 수정 후 영향을 받는 항목을 재검수한다.

필수 검증:

- 실제 저장과 여러 기기 간 조회, 재시작 후 데이터 보존.
- 회사 간 격리, 직원 소유권, 관리자·AI 권한, 인증 만료.
- 영업일·공휴일·시간대, 원래 기한 보존, 날짜 없는 업무.
- 중복 접수·중복 클릭·동시 수정·중복 승인.
- 이메일 성공/실패/인증 만료/요청 제한/결과 불명. 결과 불명은 제공자 확인 전 재발송 차단.
- 종료 전 남은 업무 확인, 종료 후 알림 중단, 수행 이력 보존.
- 모바일 입력·스크롤·오류 안내와 기존 프레임 피드백.
- AI 포함 시 근거 없는 날짜·수행 완료 생성 차단, 제안 승인과 최신 버전 검증.
- DB 백업·복원 및 배포 실패 시 복구 절차.

배포 후보 완료 기준: 합의한 MVP 흐름의 사용자 검수 완료, 데이터 손실·권한 우회·중복 발송 등 중대 오류 해결, 자동 검사 통과, 남은 제약 문서화. 목표 첫 연락 완료율 100%는 운영에서 측정할 목표이며 구축 시점에 달성한 실적으로 표시하지 않는다.

## 6.3 배포 — GitHub Actions와 Railway

기존 구조 유지: 기능 브랜치 → PR(staging) → 검사 → staging 배포·검수 → PR(main) → **본인의 GitHub 승인 → 운영 배포**.

- Railway 싱가포르 운영, Web/API/Worker/Scheduler와 PostgreSQL 구성. staging과 production의 데이터·비밀값 분리.
- 구축 중에도 PR 자동 검사 구성은 진행한다. 실제 배포 활성화는 안정화와 외부 환경 연결 후 수행한다.
- 실제 Dockerfile·CI 통합 테스트·readiness·실행 버전 확인을 구현한다. 단순 빌드 성공만으로 배포 성공 처리하지 않는다.
- GitHub Environment 승인 설정과 기존 본인 승인 검사 스크립트를 실제 저장소에서 확인한다. 승인 없이 production을 우회 배포하지 않는다.
- 배포 후 실제 URL, DB 연결, Worker/Scheduler, 검수용 접수·이메일과 복구 절차를 확인한다.

필요할 때 순서대로 확인할 연결 정보: GitHub 저장소·승인자, Railway 프로젝트·환경, CRM 도메인, Emergent API 문서·인증 방식, 메일·인증·AI 제공자와 비용 조건. 토큰·비밀번호·DB 연결 문자열은 채팅이나 Git에 넣지 않고 비밀값 저장소에 설정한다.

## 6.4 추가 구축

첫 MVP의 운영 결과와 사용자 불편을 기준으로 후속 기능을 선정한다. 요청별로 문제·예상 효과·필요 데이터·권한·검수 조건을 정하고 작은 단위로 구축·검수·승인 배포를 반복한다. AI를 첫 MVP에서 제외하는 경우 AI 연결은 우선적인 다음 후보이며, 전체 화면에 있는 기능을 구현 완료로 간주하지 않는다.
