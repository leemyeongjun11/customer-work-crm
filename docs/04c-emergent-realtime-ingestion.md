# 신규 문의 즉시 연동 및 CRM 단독 수정 명세

2026-09-12. 구현할 API 계약이며 현재 운영 중인 API를 검증한 문서는 아니다.

구현 갱신: CRM 측 서명 수신·중복 방지·원자적 저장을 [6.1 다섯 번째 구현](06e-external-inquiry-ingestion.md)에 연결했다. 실제 경로는 `POST /api/v1/integrations/emergent/inquiries`이며 아래 원래 제안 경로는 별칭으로 제공하지 않는다. 본 문서의 발신 전송기·보충 조회·SSE·5초 목표는 아직 구현·검증 전이다.

## 목표와 소유권

- 정상적인 네트워크와 합의한 부하에서 Emergent 접수 저장 → 담당자의 열린 CRM 화면 표시 p95 5초 이내를 목표로 한다.
- Emergent는 최초 접수와 원문을 보관한다. CRM은 수집 당시 원문을 별도로 보관하고 이후 고객 정보·메모·진행 상황 수정의 기준 저장소가 된다.
- CRM 수정본을 Emergent에 다시 보내지 않는다. 원문 재수신·누락 보충이 CRM 수정본을 덮어쓰지 않게 한다.
- 실제 성능은 Singapore ↔ Emergent 왕복 시간과 이벤트 전송·DB·화면을 함께 측정해 검증한다. 장애 중 즉시 표시를 보장하지 않는다.

## 정상 처리

1. 고객이 기존 Emergent 상담 폼을 제출한다.
2. 문의와 전송 대기 이벤트를 함께 저장한다. MongoDB 트랜잭션 지원을 확인하거나, 문의 문서 안의 전송 대기 정보를 함께 쓰는 단일 문서 원자적 저장을 구현한다. 두 번의 독립 저장만으로 전송 누락이 방지된다고 간주하지 않는다.
3. 별도 전송기가 저장 직후 CRM Webhook을 호출한다. 고객의 접수 성공은 원문 저장 성공으로 결정하고 CRM 연결 지연 때문에 재접수를 요구하지 않는다.
4. CRM은 서명과 내용을 검증하고 수신 이벤트·원문·CRM 수정용 초기값·담당자·첫 연락 업무·후속 자동 작업·화면 변경 기록을 한 트랜잭션으로 저장한다. AI·메일 완료를 기다리지 않는다.
5. DB 저장 성공 후 201 응답. 이미 처리한 동일 이벤트는 200 응답. DB 오류는 성공 응답하지 않는다.
6. SSE로 접근 권한이 있는 직원 화면에 상담 ID와 변경 신호를 보내고, 화면은 API에서 목록/카운트를 새로 조회한다. 민감한 원문 전체를 이벤트로 방송하지 않는다.

5초 목표를 위해 문의 수집을 15초 Scheduler 주기나 AI/메일 Worker 대기열 뒤에 두지 않는다. Web/API는 즉시 응답 가능한 상시 실행으로 운영한다.

## 제안 API

| 방향 | 경로 | 역할 |
|---|---|---|
| Emergent → CRM | `POST /api/integrations/emergent/inquiries` | 신규 문의 Webhook 수신 |
| CRM → Emergent | `GET /api/crm-export/inquiries?cursor=...&limit=100` | 최초 가져오기 및 누락 보충용 안정적인 커서 조회 |
| CRM → Emergent | `GET /api/crm-export/inquiries/{id}` | 원문 단건 재조회·오류 확인 |
| 브라우저 → CRM | `GET /api/events` | 인증된 SSE 연결 |

공개 CRM 경로의 `/api`는 Web에서 내부 API로 전달할 때 제거한다. Emergent 경로는 기존 구현에 맞게 조정할 수 있으나 필드·중복 방지·응답 계약을 함께 갱신한다.

Webhook 예시:

```json
{
  "schemaVersion": 1,
  "eventId": "고유_이벤트_ID",
  "eventType": "inquiry.created",
  "sourceInquiryId": "고유_접수_ID",
  "sourceReceivedAt": "2026-09-14T10:00:00+09:00",
  "payload": {
    "customerType": "organization",
    "name": "예시회사",
    "contactName": "홍길동",
    "phone": "010-0000-0000",
    "email": "contact@example.com",
    "requestMemo": "서비스 상담을 요청합니다."
  }
}
```

기업 구분은 인증된 연동 키에 매핑한다. 본문의 임의 기업 ID로 다른 기업 데이터를 쓰게 하지 않는다. `sourceReceivedAt`으로 원래 첫 연락 기한을 계산하고 수집 지연으로 기한을 연장하지 않는다.

서명 제안: `X-Webhook-Key-Id`, `X-Webhook-Timestamp`, `X-Webhook-Signature` 헤더. `timestamp + '.' + rawBody`의 HMAC-SHA256을 검증한다. 허용 시각 차이는 5분이며 재전송 때 현재 시각으로 다시 서명한다. eventId는 그대로 유지한다. 원문 바이트로 검증하고 키 순환 시 일정 기간 구/신 키를 허용한다.

응답 규칙: 신규 저장 201, 동일 이벤트 재전송 200, 같은 이벤트 ID의 다른 내용 409 및 검토 필요, 인증 실패 401, 스키마/필드 오류 422, 일시 장애 503. 크기 제한과 요청 제한을 적용한다. 유효한 접수의 필드 오류는 Emergent 원문·실패 기록에 남기며 보충 조회 때도 조용히 건너뛰지 않는다.

중복 기준은 `(tenant_id, source, sourceInquiryId)`와 `(tenant_id, source, eventId)`다. 다른 이벤트 ID로 같은 문의를 다시 전송해도 상담은 한 건만 만든다. 전화번호·이메일만 같다는 이유로 별도 신규 상담을 삭제하지 않는다. 같은 이벤트 ID의 payload 비교에서 전송마다 바뀌는 서명 헤더는 제외한다.

## 전달 누락과 화면 복구

- Emergent는 최초 포함 총 3회까지 일시 실패를 재시도하고 최종 실패 기록·운영 알림을 남긴다. 고객 접수 원문은 유지한다.
- CRM Scheduler가 60초 간격으로 export API의 원문/접수 로그를 조회한다. Cursor는 중복 없이 전체를 순회할 수 있는 서버 발급 값으로, 단순 클라이언트 현재 시각으로 건너뛰지 않는다.
- 같은 수집 함수를 Webhook과 보충 조회가 공유한다. 페이지 저장을 완료한 뒤에만 커서를 갱신한다. 오류 건은 영속 오류 목록에 저장하고 담당자 확인 경로를 둔다.
- 보충 조회는 문의 수집 복구다. 실패한 고객 메일의 시도 횟수를 초기화하거나 메일을 다시 등록하는 경로가 아니다.
- SSE에는 인증·담당자별 권한·연결 종료 처리를 적용한다. API 복제본들이 공유 변경 로그를 조회하고, DB 알림은 빠른 깨우기 수단으로만 사용한다.
- 재연결 시 마지막 이벤트 ID 이후를 재생한다. 보관 기간 밖이면 전체 목록을 재조회한다. 로그아웃·담당자 변경 후 권한도 다시 확인한다.
- 연결이 끊어지면 15초 간격 조회로 전환하고 연결 지연을 표시한다. 탭을 다시 열거나 포커스를 얻을 때 최신 목록을 조회한다. 복구 후에는 임시 주기 조회를 중단한다.

## 구현 합격 기준

1. 정상 신규 문의가 담당자의 열린 오늘 할 일에 나타나고 카운트도 갱신된다.
2. 동일 Webhook 연속 전송, 서로 다른 이벤트 ID의 같은 문의, Webhook/보충 조회 동시 실행에서 상담·첫 연락 업무가 한 건만 생긴다.
3. 연락처를 CRM에서 수정한 뒤 원문을 다시 수신해도 수정값이 유지된다.
4. 접수 직후 Emergent 전송기 종료, CRM 일시 중단, 응답 유실 후에도 원문과 재처리 경로가 남는다.
5. SSE 연결 중단·재접속·다른 API 복제본 연결 후 최신 목록으로 복구된다. 타 기업·비담당 직원에게 상세 정보가 유출되지 않는다.
6. 원래 접수 시각 기준으로 기한을 계산한다. 누락 보충 날짜로 바꾸지 않는다.

이 항목은 앱 구현 후 테스트할 기준이다. 현재 워크플로 파일 검사로 이 연동 기능이 구현·검증된 것은 아니다.
