# 6.1 두 번째 구현 — 고객 정보와 영업건 변경 검수

2026-09-12. 첫 실제 저장 구현에 대한 사용자 긍정 피드백 후 다음 단위를 연결했다. 기존 shadcn 테마와 `http://127.0.0.1:4180/live`를 유지한다. 전체 MVP 완료 또는 운영 배포 승인을 뜻하지 않는다.

## 추가 기능

| 위치 | 동작 | 보존·확인 기준 |
|---|---|---|
| 영업건 상세 → 고객 정보 수정 | 이름·업체명, 개인/회사, 담당자, 연락처, 이메일, 규모, 고객 요청 내용 수정 | 사유 필수. 접수 원문은 유지. 수정 전후를 변경 이력에서 조회 |
| 영업건 상세 → 영업 단계 변경 | 접수~서비스 진행의 비종료 단계 변경 | 사유·최신 상담 버전 검사. 종료·서비스 완료를 이 API로 우회 불가 |
| 상세 → 담당자 변경 | 같은 회사의 활성 사용자 선택 → 영향 확인 → 관리자 확정 | 일반 직원의 확정 차단. 미완료 업무는 새 담당자 소유로 조회. 완료한 실제 수행자는 유지 |
| 상세 → 영업건 종료 / 서비스 완료 | 사유 → 남은 업무·전후 단계 확인 → 체크 후 확정 | 미완료 기록을 완료로 바꾸지 않고 보존. 오늘/예정 목록에서 제외 |
| 상세 → 확인 대기 요청 | 미리보기 다시 열기, 확정 또는 이유를 남겨 제외 | 대기·제외 상태에서는 영업 단계와 담당자를 변경하지 않음 |

접수 당시 요청 한 줄 미리보기는 원문을 보여준다. 상세의 ‘고객 요청 내용 · 수정본’에서 정정된 내용을 조회한다. 검색은 원문과 수정본 모두 대상이다. 종료된 영업건은 상세에서 조회할 수 있으며 일반 업무 수정 버튼은 비활성화하거나 숨긴다. 영업건 종료 취소는 이번 전달 범위에 포함하지 않았다.

확인 대기 요청은 현재 직원이 직접 작성한다. AI가 만들었다고 표시하지 않는다. AI 연결은 별도 후속 작업이다. 담당자 변경의 직원 제안 API는 허용하지만, 이번 UI의 담당자 선택·확정 버튼은 관리자에게만 표시한다.

## API 추가분

공통 접두사 `/api/v1`. 기존 세션·회사/소유권 검사와 `Idempotency-Key`를 유지한다.

| 메서드·경로 | 입력/결과 |
|---|---|
| GET `/assignees` | 관리자만 같은 회사 활성 사용자 id/name/role 목록 조회 |
| PATCH `/cases/:id` | customerType/name/person/phone/email/size/requestMemo/reason/expectedVersion → 새 version |
| POST `/cases/:id/stage` | stage/reason/expectedVersion → 새 version |
| POST `/cases/:id/change-proposals` | type(close/service_complete/reassign), reason, expectedVersion, 재배정 시 proposedAssigneeId → pending 요청 |
| GET `/change-proposals/:id/preview` | 요청 상태·버전, 현재 상담·버전, 남은 업무, 새 담당자, 확정 권한 |
| POST `/change-proposals/:id/approve` | expectedCaseVersion/expectedProposalVersion/confirmed=true → 확정 및 실제 변경 |
| POST `/change-proposals/:id/reject` | expectedCaseVersion/expectedProposalVersion/reason → 제외, 업무 유지 |

확인 후 다른 수정이 먼저 저장되면 409로 차단한다. 화면에서 ‘최신 영향 다시 확인’ 후 다시 체크해야 한다. 동일 확정 요청 재전송은 저장된 결과를 돌려주고 감사 이력을 중복 생성하지 않는다. 비활성화되거나 다른 회사에 속한 대상에게 재배정할 수 없다. 생성·단계·고객 PATCH에 보호 필드를 섞으면 거부한다. 종료 후 일반 업무 수정은 차단한다.

고객·단계 수정 중 충돌은 입력을 유지하고 최신 저장 내용과 비교할 수 있다. 새로운 상세 변경창의 초안은 새로고침·로그아웃 시 영구 보존하지 않는다. 기존 연락·업무 편집창의 세션 만료 후 입력 유지와 구분한다.

## 검증 기록

- 전체 `pnpm check`: 기존 21개 + API 4개, **총 25개 테스트**, 타입 검사·웹 빌드 통과.
- 실제 HTTP로 고객 수정본/원문 분리, 보호 필드 우회, 회사 격리, 비관리자 확정 차단, 비활성 담당자, 미리보기 후 변경 충돌, 재승인 중복, 담당자 변경 후 접근권한·완료 수행자 유지, 종료 후 미완료 보존·목록 제외·수정 차단, 요청 제외와 서비스 완료 확인.
- 서버 재시작과 스키마 추가 후 기존 ‘검수 예시 · 푸른사무소’와 이전 기록 유지 확인.
- 브라우저에서 고객 요청 수정본과 변경 이력 저장, 단계 변경, 종료 요청의 최종 확인창을 확인했다. 남은 업무 1개가 표시되며 확인 체크 전 확정 버튼이 비활성화된다.
- 390px 모바일 너비에서 확인창의 가로 넘침 없음(문서 폭 390px, 확인창 폭 358px).
- 검수용 종료 요청은 ‘요청 제외’로 마쳤다. 예시 건은 제안·협의 단계에서 계속 관리하며 기존 업무가 남아 있다.

## 사용자 검수

1. 영업건 상세에서 ‘고객 정보 수정’을 눌러 예시 정보를 정정한다. 고객 요청 수정본과 접수 원문이 구분되는지 본다.
2. ‘영업 단계 변경’에서 단계·이유를 저장하고 상단 진행 단계와 이력을 확인한다.
3. ‘영업건 종료’에서 이유를 입력한 뒤 ‘변경 영향 확인’을 누른다. 남은 업무를 확인한다. 종료하지 않을 경우 ‘나중에 확인’ 또는 이유 입력 후 ‘요청 제외’를 사용한다.
4. 담당자 변경 검수는 관리자 계정으로 로그인한 뒤 진행한다. 계정 정보는 기존 `.local-data/access.txt`를 사용한다.
