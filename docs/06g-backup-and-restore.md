# 회사별 암호화 백업과 복원 검수

2026-09-13, 일곱 번째 구현 단위. 현재 **6.1 MVP 구축 중**이다. 로컬 백업 기능의 검수이며 운영 PostgreSQL 재해 복구 완료를 뜻하지 않는다.

## 직원과 관리자가 보는 기능

관리자로 `/live/settings`의 **데이터 백업**에서 이유를 입력하고 **백업 만들기**를 누른다. 회사의 고객·업무·상담·연락·사용자·변경 이력과 외부 접수 기록을 암호화해 저장하고, 별도 임시 DB에 실제 복원한 뒤 성공 여부를 표시한다. 최근 20개 생성 기록을 확인할 수 있다. 직원에게는 이 설정 화면과 API를 허용하지 않는다.

백업 대상은 로그인한 관리자의 회사 하나이다. 로그인 세션·실행 중 프로세스 상태·백업 목록 자체는 복원하지 않는다. 사용자 계정과 비밀번호 해시는 백업 안에 포함되므로 복원 후에는 기존 계정으로 다시 로그인한다.

## 구현 범위와 제한

- 동일 시점의 트랜잭션 조회, 명시적으로 관리하는 테이블을 사용한다. 최초 전달 18개에서 06h 계정 변경 이력을 포함해 19개로 확장했다. 알 수 없는 CRM 테이블이 추가되면 백업 규칙 갱신 전 생성을 차단한다.
- gzip 압축과 AES-256-GCM 암호화·변조 검사를 적용한다. 압축 전 데이터 한도는 50 MiB이다. 대규모 운영 DB의 스트리밍 백업을 대신하지 않는다.
- 파일은 `.local-data/backups/<UUID>.crmbackup`, 키는 같은 디렉터리의 `backup.key`에 저장된다. 키·암호·원본 개인정보는 응답에 노출하지 않는다. 키와 백업 파일은 Git에 넣지 않는다.
- 같은 회사·요청 키·이유의 중복 생성은 기존 결과를 반환한다. 다른 이유로 같은 키를 재사용하면 거절한다. API는 IP 기준 분당 3회로 제한한다.
- 생성 기록은 생성 중/복원 검증 완료/실패로 관리한다. 중간에 서버가 꺼지면 생성 중 상태가 남을 수 있다. 자동 재실행·자동 정리하지 않으며 관리자가 파일과 상태를 확인한 뒤 새 요청으로 재시도한다.
- 백업 파일은 자동 삭제하지 않는다. 디스크 용량·보존 기간·정기 실행·외부 저장소·키 회전은 운영 구축 대상으로 남는다.
- 파일과 키가 같은 컴퓨터에 있으면 컴퓨터 고장이나 계정 탈취에 함께 영향을 받는다. 운영자는 백업 파일과 키를 서로 구분해 접근을 제한한 별도 저장소에 보관해야 한다. Windows에서는 POSIX 파일 모드만으로 별도 ACL 보호가 보장되지 않는다.

## API

| 요청 | 동작 |
|---|---|
| `GET /api/v1/admin/backups` | 해당 회사의 최근 생성 기록 20개와 로컬 백업 모드 반환 |
| `POST /api/v1/admin/backups` | `{ "reason": "운영 기준 변경 전" }`와 `Idempotency-Key` 필요. 생성·복원 검사 후 결과 반환 |

기존 인증 쿠키·동일 출처 검사와 관리자 권한 검사를 적용한다. 기존 데이터를 덮어쓰는 복원 API나 브라우저 키 다운로드는 제공하지 않는다.

## 운영자의 별도 복원 절차

프로젝트 폴더의 PowerShell에서 아래 명령을 실행한다. `<UUID>`를 실제 백업 파일명으로 바꾸고, 마지막 인자는 **아직 존재하지 않는 새 폴더**를 지정한다.

```powershell
pnpm exec node scripts/restore-backup.mjs ".local-data/backups/<UUID>.crmbackup" ".local-data/backups/backup.key" ".local-data/restore-review-20260913"
```

1. 백업을 만든 것과 동일하거나 해당 백업의 변환 규칙을 지원하는 코드/스키마를 준비한다. 키와 파일의 조합·인증 태그·스키마 지문을 검사한다. 06h는 이 문서의 최초 전달 버전을 명시적으로 지원한다.
2. 새 디렉터리를 독점 생성하고 빈 DB에 복원한다. 이미 존재하는 폴더나 데이터가 있는 DB는 거절한다. 중간 오류는 DB 트랜잭션을 되돌린다.
3. 회사 경계·테이블별 행 수를 확인한다. 기존 로그인 세션은 되살리지 않는다. 백업에 있던 대기/재시도 알림은 보류하고 누락 복구 연결도 확인 대기로 둔다.
4. 반환된 경로와 건수를 확인하고, 별도 검수 환경에서 업무 데이터·로그인·알림 재개 여부를 확인한다. 이 명령은 실행 중인 CRM의 DB 경로를 바꾸거나 복원본을 서비스에 자동 적용하지 않는다.

실패한 새 폴더는 자동 삭제하지 않는다. 기존 DB를 열고 있는 서버와 같은 디렉터리를 별도 프로세스에서 동시에 열지 않는다. 복원본에 서버를 연결하면 향후 예약 작업은 별도로 생성될 수 있으므로, 운영 전환 전 스케줄러·발송 연결을 분리한 상태에서 검수해야 한다.

## 자동 검수

`apps/api/test/backup.test.mjs`에서 다음 세 묶음을 검증한다.

- 회사 격리·직원 차단·중복 요청·암호화 파일·디스크의 새 DB 복원·메모 보존·재로그인·세션 제외·기존 대기 알림 보류·원본 DB 유지.
- 잘못된 키·손상 파일·스키마 불일치·다른 회사가 섞인 데이터·복원 중간 오류의 롤백·기존 대상 덮어쓰기 차단.
- HTTP 인증·허용 입력·저장 실패 기록·응답의 비밀값 비노출.

실제 PostgreSQL의 백업 도구·원격 저장소·다중 프로세스 부하·복구 시간/복구 시점 목표와 운영 전환은 미검증이다. 전체 외부 연동 검수와 Railway 승인 배포도 남아 있다.

## 이번 실행 기록

전체 자동 검사 41개(업무 규칙·배포 21개, API 20개), 타입 검사, 웹 빌드가 통과했다. 로컬 서버를 백그라운드에서 재시작하고 관리자 화면에서 백업을 생성했다. 화면의 성공 안내·영업건 2개/업무 3개/사용자 2명·생성 기록을 확인했다.

현재 백업 `019ad61f-a07a-4c03-a6a7-1f4f26549d0a.crmbackup`을 운영자 명령으로 `.local-data/restore-review-20260913-019ad61f`에 실제 복원했다. 메모 2개·연락 기록 2개·변경 이력 14개를 포함한 건수 검사와 세션 0개를 확인했다. 원래 `.local-data/postgres`는 그대로 사용하며 복원본을 서비스에 연결하지 않았다. 이 복원 폴더는 로컬 검수 산출물이며 별도의 원격 백업이 아니다.
