# 6.1 첫 실제 저장 구현 — 검수 안내

2026-09-12. 사용자 요청에 따라 현재 수정된 프레임과 shadcn 기본 테마를 초기 구축 기준으로 삼았다. 첫 번째 전달 단위는 **상담 접수 → 담당자·첫 연락 기한 자동 배정 → 직원 로그인 → 결과 기록 → 다음 행동·메모 저장**이다. 전체 MVP 또는 Railway 운영 배포의 완료를 뜻하지 않는다.

## 실행 위치

- 실제 저장: <http://127.0.0.1:4180/live>
- 고객 접수: <http://127.0.0.1:4180/live/inquiry>
- 기존 52개 프레임 검수: <http://127.0.0.1:4173/review>

기존 목업은 가상 데이터 시연을 유지한다. 새 `/live` 화면은 서버 API와 파일 DB를 사용하며 실제 현재 시각으로 업무를 분류한다. 브라우저의 기존 검수 진행률을 수정하거나 자동 승인하지 않았다.

터미널에서 프로젝트 폴더를 연 뒤:

```powershell
pnpm install --frozen-lockfile
pnpm build
pnpm live:setup
pnpm live
```

`live:setup`은 최초 검수용 회사와 관리자·직원 계정을 만든다. 이미 있으면 계정을 덮어쓰지 않는다. 계정 정보는 프로젝트의 `.local-data/access.txt`에 있으며 Git에서 제외된다. 서버 실행 중에는 별도의 setup 또는 두 번째 서버로 같은 DB 파일을 열지 않는다. 종료 후 재실행할 때는 `pnpm live`만 사용한다. 화면 수정 후에는 `pnpm build` 후 브라우저를 새로고침한다.

이 전달 버전은 이 컴퓨터의 4180 포트에서만 실행한다. 모바일 너비의 브라우저 검수는 가능하며, 휴대폰에서 실제 데이터에 접근하는 인증·HTTPS 환경은 후속 스테이징 작업이다. 기존 목업의 4174 모바일 미리보기와 구분한다.

## 구현된 범위

| 항목 | 실제 동작 |
|---|---|
| 인증 | 비밀번호 해시, 서버 저장 세션, HttpOnly 쿠키, 8시간 만료, 로그아웃 |
| 권한 | 관리자는 회사 내 전체 영업건, 직원은 자신에게 배정된 영업건만 조회·변경 |
| 접수 | 입력 검사, 접수 원문 보존, 기본 직원 배정, 첫 연락 업무 생성이 하나의 DB 트랜잭션으로 처리 |
| 기한 | 한국 시간의 다음 영업일 17시. 주말·DB에 설정된 휴일 제외 |
| 오늘 할 일 | 기한 초과 / 오늘 확인 / 기한 미정, 별도 예정 업무. 완료·제외는 상세 이력으로 이동 |
| 첫 연락 | 통화 연결 또는 부재 후 문자 발송 기록 시 완료. 전화 시도만 한 경우 미완료 유지 |
| 후속 업무 | 단계별 업무 종류 선택, 상세 입력, 날짜 선택. 기타 업무는 상세 필수 |
| 메모·변경 | 메모 저장, 기한 변경, 완료·완료 취소, 업무 제외와 사유, 변경 이력 |
| 중복·충돌 | 중복 방지 키와 요청 내용 해시, 이전 버전 변경 차단, 서버 오류 시 입력 유지 |
| 재시작 | DB 파일에 저장된 상담·업무·재시도 결과가 서버 재실행 후 유지 |

연락·문자·서비스 수행 자체는 직원이 한다. 이 화면은 수행 결과를 기록한다. 통화 연결 시 접수에서 상담 진행으로 이동한다. 부재 후 문자는 첫 연락을 완료하지만 상담 단계는 접수에 남긴다. 실제 수행 시각은 접수 이후이며 미래일 수 없다. 서버 기록 시각은 별도로 남긴다.

## 실제 로컬 API

기존 4차 명세는 운영 목표 계약이다. 아래는 `/live` 화면의 첫 로컬 구현용 계약이며, 전체 4차 API 구현 완료가 아니다. 운영 경로·응답·인증 계약에 맞추는 어댑터 작업은 후속 단계에서 진행한다.

공통 접두사 `/api/v1`. 업무 변경 요청은 JSON과 `Idempotency-Key`가 필요하고 `expectedVersion`은 서버에서 받은 버전을 전달한다. 사용자·회사·담당자는 인증 세션과 서버 설정에서 결정하며 클라이언트 입력으로 권한을 선택하지 않는다.

| 메서드·경로 | 내용 |
|---|---|
| POST `/auth/login`, GET `/auth/me`, POST `/auth/logout` | 로그인·세션·로그아웃 |
| GET `/public/inquiries/:slug` | 접수 회사 표시 정보 |
| POST `/public/inquiries/:slug` | customerType/name/person/phone/email/size/memo → receiptId/receivedAt/firstContactDueAt |
| GET `/workboard` | overdue/today/upcoming/needsReview, 현재 시각·조회 상한 |
| GET `/cases?search=...`, GET `/cases/:id` | 영업건 검색, 상세·업무·메모·이력 |
| POST `/cases/:id/tasks` | taskType/description/date/expectedVersion |
| POST `/cases/:id/notes` | body/expectedVersion |
| POST `/cases/:id/contacts` | taskId/outcome/actualAt/memo/expectedVersion |
| PATCH `/tasks/:id` | date/reason/expectedVersion |
| POST `/tasks/:id/complete` | actualAt/memo/expectedVersion |
| POST `/tasks/:id/reopen`, POST `/tasks/:id/exclude` | reason/expectedVersion |

오류는 `{error:{message}}` 형식이다. 401 로그인 필요, 403 요청 출처 오류, 404 대상 없음·접근 불가, 409 버전·재시도 내용 충돌, 422 입력 오류, 429 요청 제한, 503 접수 담당자 설정 오류를 구분한다. 같은 키·내용의 성공 요청은 이전 결과를 반환한다. 키를 재사용하면서 내용을 바꾸면 409다. 세션 만료 후 재로그인하면 열린 편집창 입력을 유지한다. 버전 충돌은 최신 정보를 확인한 뒤 다시 저장한다.

## 검수 순서

1. 고객 접수 화면에서 예시 상담 한 건을 저장한다. 담당자·첫 연락 기한이 표시되는지 확인한다.
2. 직원 계정으로 로그인해 오늘 할 일과 초기 요청 한 줄을 확인한다.
3. ‘지금 연락하기’에서 전화만 시도한 결과를 저장한다. 업무가 미완료로 남는지 확인한다.
4. 다시 통화 연결 결과와 메모를 저장한다. 오늘 목록에서 빠지고 상세의 완료 기록·메모에 남는지 확인한다.
5. 상세에서 다음 행동을 선택하고 날짜 없이 저장한다. 오늘 화면의 ‘기한 확인 필요’에 보이는지 확인한다.
6. 날짜와 이유를 입력해 기한을 정하고, 새로고침·재로그인 후에도 유지되는지 확인한다.

수정 의견은 화면 이름, 수행한 동작, 예상 결과와 실제 결과로 남긴다. 검수용 데이터는 `.local-data/postgres`에 유지되며 자동 초기화하지 않는다.

## 자동 검사와 남은 범위

`pnpm check`는 기존 규칙·배포 승인 테스트, API 통합 테스트, 타입 검사와 웹 빌드를 포함한다. API 검사는 임시 DB에서 회사·직원 권한, 중복 접수, 실제 연락 기준, 동시 변경 충돌, 원래 기한 보존, 세션 만료, 파일 DB 재시작을 확인한다. 테스트는 외부 `DATABASE_URL`을 사용하지 않는다.

이번 검증: 기존 21개와 API 3개 테스트(총 24개), 타입 검사·웹 빌드 통과. 브라우저에서 예시 접수, 직원 로그인, 연락 결과·메모 저장, 다음 행동 생성, 새로고침 후 유지 확인. 모바일 너비에서 긴 요청 미리보기로 카드가 가로로 넘치는 문제를 수정하고 콘텐츠 폭과 화면 폭이 같은 것을 확인했다. 모바일 날짜 입력의 자동 조작은 도구에서 완료되지 않아 사용자 날짜 선택 검수는 남겨 둔다. 날짜 저장과 원래 기한 보존은 API 통합 검사로 확인했다. 예시 ‘검수 예시 · 푸른사무소’ 건은 사용자가 이어서 볼 수 있도록 유지했다.

첫 전달 이후 고객 정보·영업 단계·담당자 변경 및 종료를 추가 연결했다. 최신 검증은 [두 번째 구현 기록](06b-case-management-review.md)을 따른다.

첫 전달 당시 남은 범위: 누락된 다음 행동 감지, 휴일 설정 UI와 실제 운영 달력, 페이지네이션, 사용자 초대·재설정, 첨부·KPI, Emergent 수신, Worker/Scheduler, 이메일·AI 제공자, 실제 PostgreSQL 다중 접속 검증, 백업·복구, HTTPS 인증과 Railway 스테이징·운영 배포. 목록은 최근 영업건 100개, 업무 200개, 이력 100개 상한을 갖는 초기 검수용이다.

후속 갱신: 누락 감지·로컬 Worker/Scheduler는 [세 번째 구현](06c-notification-automation.md), 휴일 설정 UI·기본 첫 연락 KPI는 [네 번째 구현](06d-operations-and-metrics.md)에서 연결했다. 나머지 현재 상태는 [전체 진행 현황](06-progress.md)을 따른다.

실제 기업의 휴일이 정해지지 않아 로컬 휴일 목록은 비어 있다. 현재 토·일 제외만 자동 적용한다. 법정 공휴일을 모두 반영했다고 간주하지 않는다. 운영 전 달력 연결·검증이 필요하다.

개발용 DB는 [PGlite의 파일 저장 기능](https://pglite.dev/docs/filesystems)을 사용한다. `DATABASE_URL`이 있을 때에는 `pg` 연결 경로를 사용하도록 분리했으나 Railway PostgreSQL에서는 아직 검증하지 않았다. 운영 트랜잭션 어댑터는 [node-postgres의 동일 연결 사용 규칙](https://node-postgres.com/features/transactions)을 따른다. 로컬 서버는 production 실행을 차단하며 운영 배포 준비 상태를 false로 반환한다. 기존 GitHub 본인 승인 후 운영 배포 조건은 유지한다.
