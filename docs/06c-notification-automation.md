# 6.1 세 번째 구현 — 누락 업무 감지와 알림 처리

2026-09-13. 현재 단계는 **6.1 MVP 구축 중**이다. 실제 외부 이메일 발송 및 운영 배포는 아직 연결되지 않았다. 사용자가 GitHub·Railway·발신용 메일 서비스가 아직 준비되지 않았다고 확인했다.

## 구현된 흐름

1. 신규 상담과 첫 연락 업무를 저장할 때 고객 접수 확인·직원 접수 알림 작업도 같은 DB 트랜잭션에 저장한다. 상담 저장만 성공하고 알림 등록이 누락되는 상황을 방지한다.
2. 관리 중인 영업건에 미완료·미제외 업무가 하나도 없으면 오늘 화면의 ‘다음 행동 없음’에 표시한다. 첫 연락을 마치고 다음 업무를 등록하지 않은 경우도 포함한다. 신규 업무를 등록하면 목록에서 빠진다. 서비스 완료·종료 영업건은 제외한다.
3. 영업일 15시에는 담당자별 기한 초과·오늘 마감 업무를, 16시 30분에는 당일 마감 첫 연락 미완료만 묶는다. 대상이 없으면 생략한다.
4. 실행 직전에 완료·제외·담당자 변경·종료·날짜 변경을 다시 확인한다. 통합 알림에는 고객명·업무·기한·로그인 후 볼 상세 링크를 넣으며 상담 원문 전체를 넣지 않는다.
5. 현재 전달처는 **로컬 검수 수신함**이다. 실제 외부 수신함으로 이메일을 보내는 코드는 연결하지 않았다. 성공 상태도 `sent`가 아닌 `reviewed`이며 화면에는 ‘검수함 저장 완료 · 실제 이메일 미발송’으로 표시한다.

## 검수 화면

<http://127.0.0.1:4180/live/notifications>

- ‘내 현재 업무 알림 미리보기’는 정규 예약과 구분된 작업으로, 현재 직원의 기한 초과·오늘 마감·기한 미정·다음 행동 누락을 모아 검수함에 저장한다. 날짜나 실제 영업일을 바꾸지 않는다.
- 신규 접수 고객용 확인 내용은 관리자만 조회한다. 직원은 자기 수신 알림만 조회한다. 관리자는 회사 전체 내역을 조회한다.
- 완료된 알림은 처리 당시 내용이다. 이후 영업건 변경은 과거 알림 본문을 덮어쓰지 않는다. 상세 링크의 현재 접근 권한은 별도로 검사한다.
- ‘자동 처리 상태’에서 예약·처리의 마지막 실행 시각을 확인한다. 로컬 검수 서버를 끄면 실행되지 않는다.

## 예약과 중복 방지

영업일 달력은 회사의 휴일 설정과 토·일을 제외한다. 실제 운영 달력이 없어서 로컬 휴일 목록은 비어 있다. 법정 공휴일 반영이 완료된 상태가 아니다.

예약 키는 회사 + 알림 종류 + 한국 날짜 + 수신 직원이다. 같은 예약이 두 번 시작되어도 한 작업만 생성한다. 고객 접수 확인·직원 배정 알림은 영업건 ID별로 중복 방지한다. 수동 미리보기에는 호출자별 요청 키를 사용한다.

15시/16시 30분 이후 서버가 복구되면 당일 17시 전까지만 보충한다. 17시 이후의 예약 또는 날짜가 지난 대기는 생략 이유를 기록하고 몰아서 발송하지 않는다. 주말·휴일에는 정규 알림을 등록하지 않는다. 접수 확인 알림은 영업일 예약과 별개다.

## 실행 구조와 실패 처리

`apps/scheduler/src/run.mjs`와 `apps/worker/src/run.mjs`로 실행 역할을 나눴다. 현재 PGlite 파일 DB는 한 프로세스에서 사용하므로 로컬 API가 두 역할을 함께 실행한다. 예약 확인은 약 30초마다, 처리 확인은 약 5초마다 수행하며 한 번에 최대 20개 작업을 처리한다. Railway의 독립 프로세스 구성은 실제 PostgreSQL 연결·다중 접속 검증 후 적용한다.

작업과 본문은 DB에 보존한다. 실행 행 잠금과 검수 메시지의 jobId 고유 제약으로 동시 처리·재시도 중복을 막는다. 검수함 쓰기와 결과 기록은 같은 트랜잭션으로 처리한다. 실제 외부 서비스는 DB 트랜잭션으로 발송을 되돌릴 수 없으므로, 운영 제공자를 연결할 때 제공자 요청 식별자·결과 조회·임대 만료 복구를 추가 검증해야 한다.

| 상황 | 처리 |
|---|---|
| 명확한 일시 실패 | 최초 포함 총 3회까지 대기 후 재시도 |
| 호출 제한 | 제공된 대기 시간과 기본 대기 시간 중 긴 쪽 적용 |
| 인증 문제 | blocked, 자동 재시도 중단 |
| 데이터·응답 형식 오류 | failed, 같은 내용의 재시도 중단 |
| 결과 불명 | unknown, 확인 없이 재실행하지 않음 |
| 최종 실패·인증 문제·결과 불명 | 오늘 화면에 ‘자동 처리 확인 필요’로 연결 |

실패 유형은 로컬 제공자 오류 주입 테스트로 검증했다. 실제 메일 제공자 오류를 재현했다고 보고하지 않는다. 관리자 수동 복구·실제 제공자 결과 조회는 후속 구현 대상이다.

## API

- `GET /api/v1/notifications`: 로그인한 사용자의 권한 범위 내 검수 메시지·처리 기록(각 최대 100개), 실행 상태. `externalSending=false` 명시.
- `POST /api/v1/notifications/review`: 본문 `{}`, `Idempotency-Key` 필수. 202는 작업 등록이며 검수함 처리 완료를 뜻하지 않는다.
- `GET /api/v1/workboard`: `missingNext`, `attentionCount` 추가.

## 검증 기록

API 통합 검사에 영업일/휴일/시간 경계, 동시 예약·처리 중복, 완료 후 16시 30분 제외, 재배정 대상 재조회, 종료 후 알림 제외, 다음 행동 누락, 세 차례 실패 중단, 인증·결과 불명·호출 제한을 추가했다. 파일 DB를 다시 열었을 때 접수와 함께 저장한 알림 작업 2건도 유지됨을 확인했다.

브라우저에서 ‘알림 검수 · 새봄사무소’를 접수한 후 직원 접수 알림이 자동으로 검수함에 저장되는 것을 확인했다. 첫 연락 완료 후 다음 행동 누락 표시와 그 내용을 담은 수동 미리보기 처리도 확인했다. 사용자가 기존 예시 건에 입력한 변경과 종료 상태는 유지했다. 작성 중인 창에 간섭하지 않도록 이후 확인은 별도 검수 탭에서 수행했다.

현재 전체 검증은 기존 21개 + API 7개, 총 28개 테스트와 타입 검사·빌드다. 6.2 전체 MVP 검수 완료를 뜻하지 않는다.
