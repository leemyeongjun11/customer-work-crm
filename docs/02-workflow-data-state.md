# 2차 — 업무 흐름·데이터·상태

## 업무 흐름

1. 고객이 기존 웹사이트에서 신규 상담을 접수합니다.
2. CRM에 접수 원문을 보관하고 전담 담당자와 첫 연락 업무·기한을 연결합니다.
3. 담당자가 신청 내용을 확인합니다. 서비스 오해가 명확하면 설명 후 사유를 남겨 종료하고, 애매하면 고객에게 확인합니다. AI 판단만으로 제외하지 않습니다.
4. 전화로 요청 배경을 듣습니다. 부재 시 바로 안내 문자를 남깁니다. 정해진 자동 재통화 횟수·간격은 아직 없습니다.
5. 미팅, 회사소개서, 샘플 견적, 정식 견적 등 고객과 협의한 다음 행동을 기록합니다. 예시에 맞춰 고정된 순서를 강제하지 않습니다.
6. 고객 회신을 기다리면 현재 영업 단계를 유지하면서 다음 확인 날짜를 남깁니다.
7. 제안·협의 → 계약 → 서비스 제공으로 이어 관리합니다. 진행하지 않으면 종료 사유를 남깁니다.

별도 우선순위 등급은 두지 않습니다. 가능하면 신속히 연락하고, 화면과 알림에서는 첫 연락 지연 → 그 외 오래된 지연 업무 → 오늘 업무 순으로 확인합니다.

## 접수 데이터

| 항목 | 기준 |
|---|---|
| 이름·업체명 | 필수. 신청 개인 이름 또는 기업·업체명 |
| 고객 담당자명 | 기업·단체 고객일 때 입력. 개인은 신청자와 동일할 수 있음 |
| 연락처 | 필수 |
| 이메일 | 필수 |
| 요청 메모 | 필수 |
| 회사 규모 | 선택. 1인 / 2~9 / 10~49 / 50~299 / 300 이상 / 모름 |
| 개인·기업 구분 | 기존 명세의 데이터 구분 제안. 신청 폼 연결 시 필드 매핑 확인 필요 |

“고객 담당자”는 고객 회사의 연락 대상이고, “우리 회사 담당자”는 이 영업건을 처리할 내부 직원입니다.

## 내부 관리 데이터

| 기록 | 목적과 주요 값 |
|---|---|
| 접수 원문 | 외부 접수 ID·접수 시각·신청 원본, 이벤트 ID, 출처 |
| 영업건 | 회사 ID, 고객 정보 수정본, 내부 담당자, 영업 단계, 요약, 버전 |
| 할 일 | 영업건, 행동, 담당자, 최초/현재 기한, 기한 근거, 미완료/완료, 실제 수행자·시각 |
| 기한 확인 | 날짜가 없으면 `dueAt=null`, `deadlineStatus=needs_confirmation` |
| 메모·자료 | 상담 메모 버전, 첨부 자료와 소유 영업건. 업로드를 발송 완료로 보지 않음 |
| 제안·승인 | 근거, 연결 업무, 검토 날짜, 대기/승인/제외, 승인자·변경 이유·대상 버전 |
| 변경 이력 | 수행 주체, 변경 전후 값, 근거, 시각. AI 변경과 되돌리기 포함 |
| 자동 실행 | 발송·분석·연동 작업 ID, 중복 방지 키, 재시도·실패·수동 확인 상태 |

CRM에서 수정한 값은 CRM에서 관리합니다. Emergent 재전송·보정 수집으로 CRM 수정본을 덮어쓰지 않습니다. 외부 MongoDB 직접 수정 대신 API 방식으로 연결합니다.

## 상태 정의

영업 단계: **접수 / 상담 진행 / 제안·협의 / 계약 완료 / 서비스 진행 / 서비스 완료 / 종료**.

업무 상태: **미완료 / 완료** 두 가지. 기한 초과는 날짜에 따라 계산되는 표시입니다. 관리 제외는 별도 표시·사유로 남기고 완료 실적에 넣지 않습니다.

승인 대기 중에는 실제 영업 상태와 알림을 유지합니다. 종료할 때 남은 미완료 업무·중단되는 알림을 확인하고, 종료 후에도 미완료·완료 기록을 보관합니다. 담당자 변경은 관련 미완료 업무에 반영하되 완료 이력의 실제 수행자를 바꾸지 않습니다.

후속 이메일은 직원 검토 후 실제 발송 성공이 확인되어야 완료됩니다. 회신 확인은 별도 업무입니다. 발송 결과 불명은 실패와 구분하고 재발송 전에 제공자 결과를 조회해야 합니다.

## 이번 프레임의 표현 범위

날짜와 수신 이벤트는 고정된 가상 데이터로 시연합니다. 운영용 영업일 계산, 자료 업로드, 서버 버전 검사, API 재시도는 아직 구현하지 않았습니다. 실제 API 필드명·오류는 [04d](04d-core-api-contract.md)를 기준으로 연결합니다.
