# 다섯 번째 구현 — 외부 신규 문의 수신

현재 **6.1 MVP 구축 중**. Emergent가 보낸 신규 문의를 검증하여 저장하는 CRM 측 수신기를 구현했다. 실제 Emergent 연결이나 즉시 화면 표시 목표를 달성했다는 뜻은 아니다.

## 구현한 흐름

서명 확인 → 이벤트·필드 검사 → 회사와 담당자 확인 → 원문·상담·첫 연락 업무·알림 작업·수신 이력을 한 트랜잭션으로 저장 → 저장 결과 응답.

기존 직접 접수와 외부 접수는 같은 입력 검사와 상담 생성 함수를 사용한다. 별도의 AI 분석이나 이메일 발송이 끝나기를 기다리지 않는다. 알림은 기존 로컬 검수 수신함으로만 처리한다.

중복 식별은 회사별 원본 문의 ID와 이벤트 ID를 모두 사용한다. 같은 문의를 동시에 여러 번 보내거나 이벤트 ID를 바꿔 보내도 상담과 알림이 다시 생성되지 않는다. 같은 ID로 다른 내용을 보내면 409로 중단하며 CRM 수정본은 유지한다. 이름·전화·이메일이 같아도 원본 문의 ID가 다르면 별개의 신규 상담이다.

첫 연락 기한은 CRM에 도착한 시간이 아닌 **원래 접수 시각**에서 계산한다. 수집 시각은 별도 기록한다. 회사에 현재 설정된 휴일·담당자 정책을 적용하여 보존한다. 과거 휴일 정책을 자동 복원하는 기능은 아니다.

## 실제 구현 API 계약

`POST /api/v1/integrations/emergent/inquiries`

04c의 제안 경로를 현재 API의 `/api/v1` 접두사에 맞췄다. 기존 제안 경로는 별칭으로 제공하지 않는다. 운영 호스트 공개는 아직 비활성이고 현재 로컬 검수 주소에서만 실행된다.

필수 헤더:

- `Content-Type: application/json`
- `X-Webhook-Key-Id`: 서버가 미리 등록한 키 ID
- `X-Webhook-Timestamp`: 현재 Unix 초, 10자리 문자열
- `X-Webhook-Signature`: `timestamp + '.' + rawBody`의 HMAC-SHA256 결과, 소문자 16진수 64자리

서명 검증은 JSON을 다시 직렬화한 값이 아닌 수신 원문 바이트에 적용한다. 허용 시각 차이는 최대 5분이다. 재전송 시 이벤트 ID와 본문을 유지하고 현재 시각으로 다시 서명한다. 일반 사용자 API의 출처 검사 예외는 이 서명 수신 경로에만 적용한다.

```json
{
  "schemaVersion": 1,
  "eventId": "event-001",
  "eventType": "inquiry.created",
  "sourceInquiryId": "inquiry-001",
  "sourceReceivedAt": "2026-09-11T10:00:00+09:00",
  "payload": {
    "customerType": "organization",
    "name": "검수 예시 업체",
    "contactName": "검수 담당자",
    "phone": "010-0000-0000",
    "email": "example@example.com",
    "companySize": "10명 미만",
    "requestMemo": "시설 점검 상담을 요청합니다."
  }
}
```

회사 접수는 `organization`, 개인은 `person`이다. 회사 접수는 `contactName`이 필요하고 개인 접수는 `name`을 담당자명으로 사용한다. `companySize`는 선택이다. 원래 접수 시각은 시간대를 포함해야 하며 미래 날짜는 거부한다. ID는 영문·숫자·밑줄·마침표·콜론·하이픈으로 1~128자다. 본문에 임의 회사 ID·담당자·권한을 지정할 수 없다.

| 응답 | 의미·발신 측 처리 |
|---|---|
| 201 | 신규 저장 완료. `receiptId`, `receivedAt`, `firstContactDueAt`, `duplicate:false` |
| 200 | 이미 저장된 동일 문의. 최초 결과와 `duplicate:true`, 추가 생성 없음 |
| 400 / 415 / 422 | JSON / 형식 / 필드 오류. 내용을 확인 |
| 401 | 키·서명·시각·키 만료 오류. 자동 재시도 중단 후 설정 확인 |
| 409 | 같은 ID의 내용 불일치. 원문과 CRM 수정본 검토 |
| 413 | 본문 16KiB 초과 |
| 429 | IP 기준 프로세스당 분당 120회 초과. `Retry-After: 60`에 따라 대기 |
| 503 | 연결 미설정 또는 저장 실패. 미설정이면 운영자 확인, 일시 저장 실패이면 동일 ID로 재전송 |

일반 저장 오류도 성공으로 응답하지 않는다. 실패한 트랜잭션은 문의·업무·알림·이력을 모두 롤백한다. 발신 측은 응답 유실 시 동일 이벤트를 재전송할 수 있다.

## 키 설정과 적용 경계

서버 환경변수 `CRM_EMERGENT_KEYS`는 `id`, `tenantId`, `secret`, `expiresAt`을 가진 객체 배열 JSON이다. 실제 비밀값은 Git이나 문서에 넣지 않는다. 키는 32바이트 이상이고 회사 UUID와 시간대가 포함된 만료 시각이 필요하다. 구·신 키를 함께 등록하여 순환할 수 있고 만료된 키는 거부한다. 현재는 키를 설정하지 않아 외부 수신을 503으로 차단한다. 변경 후 서버 재시작이 필요하다.

회사 식별은 검증된 키에서만 가져온다. 현재 로컬 API의 호스트 제한은 유지했다. 운영 공개·HTTPS·분산 요청 제한·비밀값 관리·키 발급 화면은 후속 구현 대상이다.

## 검수 결과

`pnpm check`에서 총 **33개 검사**(기존 규칙/배포 검사 21개 + API 검사 12개), 타입 검사, 웹 빌드 통과.

- 실제 HTTP 요청으로 위조 서명, 오래된/미래 서명 시각, 만료/미등록 키, 훼손된 본문, 잘못된 필드, 초과 크기를 검사했다.
- 동시 재전송·다른 이벤트 ID·키 순환·회사 분리·CRM 수정본 보존을 격리 DB에서 검사했다.
- 9월 11일 접수를 16일에 수신해도 원래 기한이 14일 17시로 유지됨을 확인했다.
- 마지막 수신 이력 저장에 장애를 주어 모든 저장이 롤백되고 재전송으로 복구됨을 확인했다.
- 검수는 격리된 예시 DB에서 실행했으며 사용자가 입력한 로컬 상담은 수정하지 않았다. 로컬 서버를 새 코드로 실행했다.
