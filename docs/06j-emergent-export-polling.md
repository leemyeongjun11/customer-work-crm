# 문의 누락 조회 어댑터와 주기 실행

2026-09-13. CRM 쪽 조회 연결과 예약 코드를 구현했다. 실제 Emergent API·인증 정보는 미연결이며 원격 송수신·5초 표시 목표 검증은 아직 수행하지 않았다.

## 연결 계약

Emergent는 `GET /api/crm-export/inquiries?cursor=...&limit=100` 같은 조회 전용 엔드포인트를 제공한다. 실제 경로는 설정에 지정할 수 있다. Bearer 토큰은 해당 회사의 원문 조회만 허용하는 별도 자격증명을 사용한다. 이 인증 방식은 연결 구현 기준이며 기존 Emergent에서 이미 지원된다고 가정하지 않는다.

응답은 `Content-Type: application/json`과 다음 구조이다.

```json
{"items": [], "nextCursor": "서버가 발급한 다음 위치", "hasMore": false}
```

items에는 06e 수신 API와 동일한 `schemaVersion`, `eventId`, `eventType`, `sourceInquiryId`, `sourceReceivedAt`, `payload` 이벤트가 최대 100개 들어간다. 개인/기업 구분은 `person`/`company`이며 현재 수신 API의 필드를 따른다. 초기 cursor가 없으면 안정적인 시작 위치부터 조회하고, 마지막 페이지도 빈 문자열이 아닌 다음 조회 위치를 반환한다.

## 서버 설정

`CRM_EMERGENT_EXPORTS`를 JSON 배열로 설정한다. 각 항목은 회사 UUID `tenantId`, 쿼리 없는 HTTPS 전체 조회 주소 `endpoint`, 공백 없는 조회 전용 인증값 `token`이다. 최대 10개 회사를 허용하며 같은 회사 중복 연결을 거절한다. 실제 비밀값을 문서·Git·채팅에 넣지 않는다.

값이 없으면 조회 함수와 예약을 활성화하지 않는다. 연결되지 않은 회사의 관리자 화면은 계속 ‘연결 준비 전’으로 표시한다. 다른 회사에 설정된 인증값을 재사용하거나, 요청 본문으로 회사를 선택할 수 없다. 값 변경은 서버 재시작 후 반영한다.

## 실행과 실패 처리

- 설정된 회사만 서버 시작 시 확인하고 이후 60초 주기로 확인한다. 회사별 DB 커서·next_run·실행 임대를 기존 복구 엔진이 관리한다. 이미 실행 중이면 겹쳐 시작하지 않는다.
- 1회에 1페이지를 처리한다. 페이지에 오류가 있으면 원래 조회 위치를 유지하고 성공한 건은 재조회돼도 중복 생성하지 않는다. 다음 주기에 이어 처리하므로 밀린 물량의 회복 속도는 별도 부하 검증 대상이다.
- 조회는 10초 제한, 응답은 최대 1 MiB이다. 리다이렉트를 따르지 않는다. 인증 실패 401/403은 중단하고 관리자 확인 후 재개한다. 429의 Retry-After는 60초~24시간 범위에서 적용한다. 그 외 연결/응답 실패는 다음 주기에 재확인한다.
- 오류 응답의 원문이나 인증값을 화면에 표시하지 않는다. HTML·깨진 JSON·너무 큰 응답은 저장 전에 거절한다.
- 문의 조회 예약은 로컬 기한 알림 예약과 별도로 실행한다. 느린 조회 때문에 알림 실행이 기다리지 않는다. 정상 종료 시 현재 조회를 기다린 뒤 DB를 닫는다.

현재 로컬에서는 API 프로세스가 별도의 주기 실행 루프를 관리한다. 독립 Railway Scheduler 서비스에서의 배포·다중 프로세스 검증은 아직 남아 있다. 연결 설정만으로 Webhook 발신 전송기가 구현되거나 실제 성능이 검증되지는 않는다.
