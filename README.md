# 고객 대응 누락을 줄이는 업무 관리 CRM

고객의 상담 요청을 접수하고, **누가 언제 무엇을 해야 하는지** 관리하는 AI 리빙랩 프로젝트입니다. 전화나 기억에 의존하다가 첫 연락·견적 전달·후속 확인을 놓치는 문제를 줄이는 것을 목표로 합니다. 실제 기업에서의 시간 절감·누락 감소 효과는 아직 검증 전입니다.

**현재 상태 — 2026-09-13:** 실제 기록을 저장하는 CRM을 Railway 시험 환경에 배포했습니다. GitHub 자동 검사와 시험 환경 자동 배포도 연결됐습니다. 현재 사용·검수하는 최신 코드는 **`staging` 브랜치**이며, 정식 운영 환경(`production`) 배포와 전체 운영 검수는 남아 있습니다. 실제 AI 모델은 아직 연결하지 않았습니다.

## 어떤 순서로 사용하는가

예: 고객이 “에어컨 3대 점검 견적을 부탁합니다”라고 신청한 경우입니다.

1. **상담 접수:** 신청서가 저장되면 설정된 기준에 따라 담당자와 첫 연락 기한을 배정합니다.
2. **첫 연락:** 직원이 오늘 할 일에서 요청을 확인하고 직접 전화한 뒤 연락 결과와 상담 메모를 기록합니다.
3. **다음 업무 결정:** 현재 고객 상황을 선택하면 다음 업무와 영업 단계의 등록안이 나옵니다. 직원이 내용·날짜를 확인하고 승인합니다.
4. **실제 업무 수행:** 직원이 견적서를 작성·전달하고 해당 업무의 완료를 기록합니다. 버튼만 눌러 견적서나 문자가 발송되는 것은 아닙니다.
5. **후속 진행:** 완료 뒤 안내에서 ‘고객 답변을 기다리고 있어요’를 선택하면 ‘견적 답변 확인’ 업무와 ‘제안·협의’ 단계를 함께 확인·승인할 수 있습니다.
6. **계약부터 종료까지:** 실제 진행 상황에 맞춰 계약 확정·서비스 진행·서비스 완료를 기록합니다. 개별 업무 하나를 완료한 것과 고객의 전체 요청이 끝난 것은 구분합니다.

상담 후 다른 사람이 **같은 실제 요청**으로 연락한 것을 확인하면 기존 영업건과 연결할 수도 있습니다. 업체명이 같은 후보를 보여 주며, 부서·장소·요청 내용까지 같은지는 직원이 확인합니다. 같은 회사의 2층 에어컨과 4층 실외기처럼 서로 다른 요청은 별도로 유지합니다.

## 현재 구현된 기능

| 기능 | 현재 할 수 있는 일 |
|---|---|
| 오늘 할 일·예정 업무 | 기한 초과, 오늘 확인, 기한 확인 필요, 다음 할 일 등록 필요를 확인하고 처리 |
| 상담과 영업건 | 상담 접수, 담당자 배정, 고객 정보·연락 결과·상담 메모·변경 이력 저장 |
| 업무 완료 후 안내 | 고객 상황에 맞는 다음 업무와 단계 제시, 수정·승인 후 함께 저장, 미결정 안내 다시 열기 |
| 같은 요청 연결 | 기존 건과 비교·확인 후 한곳에서 관리, 연락처·메모·이력 보존, 가져올 업무 선택 |
| 단계·담당자 관리 | 영업 단계 변경, 담당자 변경과 종료 전 영향 확인 |
| 알림·운영 기준 | 다음 행동 누락 감지, 영업일 알림 예약·검수용 수신함, 기본 담당자·휴일 설정, 첫 연락 성과 조회 |
| 계정·권한 | 로그인, 관리자/담당자 접근 제한, 등록된 직원의 사용 중지·재개와 인계 확인 |
| 배포·검사 | 실제 PostgreSQL 검사, 네 서비스 컨테이너 검사, 시험 환경 자동 배포와 실행 상태 확인 |

같은 요청으로 연결할 때 기존 건의 업무는 유지합니다. 추가 건에서 가져오지 않는 업무는 삭제하지 않고 관리 제외 기록으로 남깁니다. 자세한 사용법은 [완료 후 안내와 같은 요청 연결](docs/06n-follow-up-and-linked-requests.md)을 참고합니다.

## AI는 어느 부분에 들어가는가

향후 AI의 역할은 **기존 고객 메시지나 상담 기록을 읽고, 요약·다음 업무·날짜·같은 요청 후보를 정리해 직원이 확인할 등록안을 준비하는 것**입니다. 실제 고객 연락과 견적 작성·전달은 현재 직원이 수행합니다.

현재 구현은 다음과 같습니다.

- **실제 CRM의 다음 진행 안내:** 직원이 선택한 고객 상황과 미리 정한 규칙으로 등록안을 만듭니다. 상담 내용을 AI가 읽어 판단하는 기능은 아직 없습니다.
- **같은 요청 후보:** 업체명 일치 여부로 찾습니다. 실제로 같은 부탁인지 자동 판단하거나 자동으로 합치지 않습니다.
- **별도의 AI 시연 화면:** 미리 작성한 시나리오로 미래 사용 흐름을 체험합니다. 실제 AI 분석 결과가 아닙니다.

실제 AI 연결, 통화 자동 녹음·음성의 텍스트 변환, 실제 이메일·문자 발송, Emergent 외부 문의 연결은 아직 미구현 또는 비활성입니다. 외부 문의 수신·중복 방지·조회·복구 처리 코드는 있지만 실제 외부 서비스와 연결한 상태는 아닙니다.

## GitHub·Railway와 CI/CD

| 이름 | 이 프로젝트에서 하는 일 |
|---|---|
| GitHub | 코드·문서·변경 이력을 보관하고, GitHub Actions로 작성해 둔 검사를 실행 |
| Railway | 웹·API·알림 처리·예약 서비스를 실행하고 PostgreSQL DB를 보관 |
| staging | 변경한 앱을 먼저 사용하고 확인하는 시험 브랜치와 배포 환경 |
| main / production | 운영 배포 후보 코드 / 정식 운영 환경. 현재 운영 배포는 비활성 |

현재 개발 흐름은 **수정 → 커밋 → GitHub 푸시 → PR 검사 → staging 병합 → 자동 검사 → Railway 시험 배포 → 실행 상태 확인**입니다.

- **커밋(commit):** 변경 내용을 Git 이력에 기록합니다.
- **푸시(push):** 로컬 커밋을 GitHub에 올립니다. 작업 브랜치에 푸시하는 것만으로 시험 사이트가 바뀌지는 않습니다.
- **PR / 병합(merge):** 작업 내용을 검토하고 대상 브랜치에 반영합니다.
- **CI:** 타입·업무 규칙·저장·권한·PostgreSQL·빌드·컨테이너 기동을 자동으로 검사합니다.
- **CD:** `staging`에 반영된 변경이 검사를 통과하면 Railway 시험 환경을 배포합니다. PR 검사에서 배포 항목이 `Skipped`인 것은 정상입니다.

정식 운영 배포는 준비와 검수 완료 후 본인이 GitHub의 **운영 배포 실행**을 수동으로 시작하는 별도 절차입니다. `main`에 반영하는 것만으로 운영 배포가 시작되지 않습니다. [배포 절차](docs/06k-owner-triggered-deployment.md) · [시험 실행 환경](docs/06l-staging-runtime.md)

## 개발자용 로컬 실행

사이트를 사용하기만 할 때는 위 시험 URL로 접속하면 됩니다. 아래는 코드를 수정하거나 자신의 PC에서 실행할 때 쓰는 명령입니다. **Node.js 24와 pnpm 11.19.0**이 필요하며 프로젝트 폴더의 PowerShell에서 실행합니다.

### 실제 저장 CRM 실행

```powershell
pnpm install --frozen-lockfile
pnpm build
pnpm live:setup
pnpm live
```

브라우저에서 [로컬 CRM](http://127.0.0.1:4180/live)을 엽니다. 최초 계정은 `.local-data/access.txt`, 로컬 DB는 `.local-data/postgres`에 보관합니다. `live:setup`은 최초 실행 전에 한 번 수행하고, 이후에는 `pnpm live`로 실행합니다. 로컬 데이터와 Railway 시험 데이터는 별개입니다. 종료는 `Ctrl+C`입니다.

Windows 숨김 백그라운드 실행은 `./scripts/start-live.ps1`을 사용합니다. 중복 실행을 방지하며 로그는 `.local-data/live-server.out.log`와 `.local-data/live-server.err.log`에 남습니다. 컴퓨터 재시작 후에는 다시 실행해야 합니다.

### 화면 개발과 기존 프레임 검수

```powershell
pnpm dev
```

[개발 화면](http://127.0.0.1:5173)을 실행합니다. 이 명령은 웹 개발 서버만 시작합니다. 실제 저장 CRM의 실행 절차는 위의 `pnpm live`를 사용합니다.

빌드한 기존 목업은 `pnpm build` 후 `pnpm --filter @crm/web preview`를 실행하고 [프레임 검수 화면](http://127.0.0.1:4173/review)을 엽니다. 기존 프레임은 가상 데이터이며 기준 시각은 2026-09-14 15:00 KST로 고정돼 있습니다. 업무 데이터는 새로고침하면 초기화되고, 52개 화면의 검수 선택값은 별도로 브라우저에 보관됩니다.

같은 Wi-Fi의 휴대폰에서는 `pnpm --filter @crm/web preview:mobile` 실행 후 터미널에 출력된 `Network` 주소의 `/review`로 접속합니다. PC와 서버가 켜져 있어야 합니다. `127.0.0.1`은 접속하는 기기 자신의 주소이므로 다른 사람에게 공유하는 인터넷 주소가 아닙니다.

### 자동 검사

```powershell
pnpm check
```

타입 검사, 업무 규칙·배포 승인·API 저장/권한 테스트, 웹 빌드를 실행합니다. 빌드 결과는 `apps/web/dist`입니다. 별도의 `pnpm test:postgres`는 전용 시험 DB 설정이 필요합니다. 실제 PostgreSQL 및 컨테이너 검사는 GitHub CI에서도 실행합니다. 검사 기록은 [진행 현황](docs/06-progress.md)에 남깁니다.

## 프로젝트 구성

프런트엔드는 React + TypeScript + Vite + Tailwind CSS v4 + shadcn/ui를 사용합니다. [UI 기술·테마 기준](docs/05a-ui-stack-theme.md)

```text
apps/web/           직원·고객 화면, AI 시연, 웹 서비스
apps/api/           인증·권한·상담·업무·메모·요청 연결 API
apps/worker/        예약된 알림 처리
apps/scheduler/     영업일 알림 예약과 외부 문의 누락 확인
packages/domain/   업무 규칙·가상 데이터·테스트
docs/              설계·구현·검수 기록
infra/railway/     Railway 서비스 설정과 연결 안내
scripts/          실행·인프라·승인·릴리스 검사 도구
.github/workflows/ 자동 검사·시험 배포·수동 운영 배포
```

로컬 검수에서는 API·worker·scheduler를 한 프로세스에서 실행합니다. Railway에서는 **web·api·worker·scheduler를 각각의 서비스**로 실행하며 PostgreSQL을 공유합니다.
